# AdaptiveDB — Adaptive Consistency Distributed Key-Value Database

AdaptiveDB is a fault-tolerant, replicated distributed key-value database featuring configurable and dynamically adaptive consistency levels across PostgreSQL replicas with a centralized gRPC coordinator.

---

## 1. Project Overview & Architecture

AdaptiveDB decouples storage replicas from client interaction using a coordinator architecture. Clients issue requests via gRPC to the Coordinator, which orchestrates quorum math, consistency enforcement, conflict resolution, asynchronous background replication, and anti-entropy recovery across 4 PostgreSQL database nodes.

```
Client (CLI / Benchmark)
   │
   │ gRPC (Port 50051)
   ▼
Coordinator Server (server.py)
   ├── Consistency Manager (consistency.py)
   ├── Adaptive Controller (adaptive.py)
   ├── Metrics Collector (metrics.py)
   └── Replication Layer (replication.py)
        │
        ├── Concurrent Replicate (ThreadPoolExecutor)
        ├── Anti-Entropy Node Recovery Engine
        └── Read-Repair Engine
        /       |       \       \
       ▼        ▼        ▼       ▼
    Node 1   Node 2   Node 3   Node 4
    (5433)   (5434)   (5435)   (5436)
  PostgreSQL PostgreSQL PostgreSQL PostgreSQL
```

## 3. Database Model & Conflict Resolution

### Schema
```sql
CREATE TABLE IF NOT EXISTS kv_store (
    key TEXT PRIMARY KEY,
    value TEXT,
    version BIGINT NOT NULL,
    deleted BOOLEAN NOT NULL DEFAULT FALSE,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### Key Semantics:
1. **Monotonically Increasing Logical Clock**: Every write (PUT / DELETE) receives an incremental logical version generated by the coordinator.
2. **Safe Conflict Resolution**: Writes execute with `WHERE kv_store.version <= EXCLUDED.version`, ensuring delayed replication messages can never overwrite newer data.
3. **Tombstone Deletions**: Deletes store `deleted = TRUE` and `value = NULL` with a higher version, preventing deleted rows from being resurrected by stale replicas.

---

## 4. Consistency Models (4-Node Quorum)

| Consistency Level | Required ACKs ($N=4$) | Write Behavior | Read Behavior |
| :--- | :---: | :--- | :--- |
| **STRONG** | **4 / 4** | Concurrent write to all 4 nodes; requires all 4 to acknowledge. | Queries all 4 replicas; returns newest version; triggers read repair on stale replicas. |
| **QUORUM** | **3 / 4** | Strict majority ($\lfloor N/2 \rfloor + 1 = 3$). Returns as soon as 3 ACKs succeed. | Queries replicas until quorum is satisfied; returns newest version; detects version divergence. |
| **EVENTUAL** | **1 / 4** | Fast path: returns immediately after 1 primary node acknowledges. Replicates asynchronously to remaining nodes with same version. | Queries fastest available replica immediately. Detects if read is stale relative to cluster state. |
| **ADAPTIVE** | Dynamic | Dynamically chooses between `STRONG`, `QUORUM`, and `EVENTUAL` based on live cluster health, latency, and throughput. | Executes using the adaptively selected consistency mode. |

---

## 5. Adaptive Consistency Controller

The `AdaptiveController` uses real-time runtime signals:
- Number of alive replicas
- Average operation latency
- Request rate (load)
- Read/Write ratio
- Replica failure rate

### Decision Policy:
1. **Degraded Cluster ($\le 2$ nodes alive)**: Falls back to `EVENTUAL` (since majority quorum cannot be met).
2. **1 Node Down (3 nodes alive)**: Selects `QUORUM` if latency $< 150\text{ms}$; falls back to `EVENTUAL` under severe network degradation.
3. **All 4 Nodes Healthy**:
   - Low latency ($< 60\text{ms}$) & moderate load: **`STRONG`**
   - Moderate latency ($60\text{ms} - 150\text{ms}$) or high request rate: **`QUORUM`**
   - High latency ($> 150\text{ms}$) or packet drops: **`EVENTUAL`**

All decisions are logged in the format:
```text
[Adaptive] alive_nodes=4/4 avg_latency=32.4ms request_rate=45.0 selected=STRONG
```

---

## 6. Failure Handling & Anti-Entropy Recovery

1. **Non-blocking Failure Detection**: All PostgreSQL queries use connection timeouts (`CONNECT_TIMEOUT=2s`), preventing node failures from hanging the coordinator.
2. **Asynchronous Read Repair**: When a read operation detects a replica with an outdated version or missing key, a background task synchronizes the latest version to that replica.
3. **Automated Node Recovery (Anti-Entropy)**: A background monitor detects when a failed node transitions from `DOWN` to `UP` and reconciles its database by copying missing or newer records from healthy replicas while preserving tombstones.

## 8. How to Run

### Step 1: Start PostgreSQL Replicas
```powershell
docker compose up -d
```

### Step 2: Install Python Dependencies
```powershell
pip install -r requirements.txt
```

### Step 3: (Optional) Recompile Protobuf Files
```powershell
python -m grpc_tools.protoc -Iapp/proto --python_out=app/proto --grpc_python_out=app/proto app/proto/database.proto
```

### Step 4: Start the Coordinator Server
```powershell
cd app
python server.py
```

### Step 5: Run the Client
In a second terminal:
```powershell
cd app

# Run automated demo suite:
python client.py --demo

# Or perform individual operations with explicit consistency:
python client.py --op put --key user101 --value 5000 --consistency STRONG
python client.py --op get --key user101 --consistency QUORUM
python client.py --op delete --key user101 --consistency EVENTUAL
python client.py --op put --key user102 --value 9999 --consistency ADAPTIVE
python client.py --op health
python client.py --op stats
```

## 10. Phase 2: Fault-Injection Testing & Adaptive Controller Validation

Phase 2 introduces a centralized, reproducible application-level fault-injection framework to validate the **Adaptive Consistency Controller** under varying network delays, node degradation, replication lag, and random drops.

```
                      Client Request
                            │
                            ▼
             Coordinator Server (server.py)
                            │
               AdaptiveController (v2.0)
       (Hysteresis + Cooldown + Health Cache + Signals)
                            │
                            ▼
                    ReplicationManager
                            │
   ┌────────────────────────┼────────────────────────┐
   │                        │                        │
Foreground Writes     Asynchronous Rep        Anti-Entropy
 (Delay + Drops)     (Replication Delay)        Recovery
   │                        │                        │
   ▼                        ▼                        ▼
Node 1 (5433)         Node 2 (5434)            Node 3 (5435) / Node 4 (5436)
```

### 10.1 Centralized Fault-Injection Configuration
Configurable via environment variables or the programmatic `fault_injector.override(...)` context manager:

| Environment Variable | Default | Description & Tested Values |
| :--- | :---: | :--- |
| `FAULT_INJECTION_ENABLED` | `false` | Master toggle for application-level fault injection. |
| `SIMULATED_DELAY_MS` | `0` | Per-interaction network latency (0ms, 25ms, 50ms, 100ms). |
| `SIMULATED_DELAY_JITTER_MS` | `0` | Bounded uniform jitter added to delay: $[-\text{jitter}, +\text{jitter}]$. |
| `SIMULATED_FAILURE_PROBABILITY`| `0.0` | Probability of simulated packet drop per interaction (0.0, 0.05, 0.10, 0.25). |
| `SIMULATED_REPLICATION_DELAY_MS`| `0` | Delay applied specifically to asynchronous background replication (0ms, 50ms, 100ms, 250ms). |
| `HEALTH_CACHE_TTL_SECONDS` | `1.0` | Node health cache TTL to avoid live TCP overhead on fast path. |
| `CONNECT_TIMEOUT_SECONDS` | `2` | PostgreSQL socket connection timeout. |

### 10.2 Phase 2 Experiment Matrix

The automated benchmark runner executes 6 core experiment suites:

- **Experiment A (Baseline)**: 4/4 nodes healthy, 0 ms delay, 0% failures.
- **Experiment B (Increasing Delay)**: 0 ms, 25 ms, 50 ms, 100 ms network latency.
- **Experiment C (Partial Node Failure)**: 4/4, 3/4, 2/4, 1/4 available replicas.
  - *STRONG*: Requires 4/4 ACKs; fails writes when $\le 3$ nodes available.
  - *QUORUM*: Requires 3/4 ACKs; succeeds with 3/4, fails with $\le 2$ nodes.
  - *EVENTUAL*: Requires 1/4 ACK; succeeds with $\ge 1$ node.
  - *ADAPTIVE*: Automatically switches to QUORUM (3 nodes) or EVENTUAL ($\le 2$ nodes).
- **Experiment D (Replication Lag)**: 0 ms, 50 ms, 100 ms, 250 ms replication delay to induce and measure stale reads before convergence.
- **Experiment E (Random Operation Failures)**: 0%, 5%, 10%, 25% failure probabilities.
- **Experiment F (Combined Faults)**: Multi-fault combinations (e.g. 50ms delay + 3/4 nodes, 100ms delay + 2/4 nodes).

### 10.7 Artifact Outputs & Interpretation

All experiment outputs are preserved in `results/`:

- `results/adaptive_decisions.csv`: Decision trace for every adaptive choice (controller version, timestamp, signals, selected mode, reasoning).

## 11. Known Limitations & Research Boundaries

1. **Application-Level Delay Simulation**: In-process delays simulate request/response round-trip latency at the coordinator boundary. They do not emulate kernel-level packet drops, TCP window throttling, or asymmetric network partitions.
2. **PACELC & Linearizability**: Quorum acknowledgement policies ($R+W > N$) protect against stale reads under static majorities, but acknowledge thresholds alone do not guarantee strict linearizability without distributed consensus protocols (e.g. Raft/Paxos) or synchronized clocks (e.g. TrueTime).
3. **Decoupled Architecture for ML Extension**: The `AdaptiveController.choose_consistency(...)` interface is decoupled to facilitate swapping the deterministic rule-based policy with a trained reinforcement learning or neural policy without modifying the storage or replication layers.
